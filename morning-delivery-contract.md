# Phase 15.1 — Morning Report delivery contract

Production target: one immutable Morning Report per Asia/Taipei date, fixed baseline cutoff at 08:30 local (`00:30 UTC`). The first valid create-only date file on `morning-reports` remains canonical. Later executions discover that file before reading new intelligence, and publish exactly the same public projection. Intraday market data cannot rewrite it. A new local date has a new independent key. GitHub's cron start can be delayed; `baseline_timestamp` states the source cutoff, while `generated_at` and delivery status state actual execution time. This contract does not promise exact 08:30 arrival from GitHub scheduling.

## Lifecycle

1. Scheduled trigger at 08:30 and one bounded scheduled retry at 09:06 Taipei. The retry omits an additional LLM call; other workflow modules run as before. Manual same-day recovery remains possible until the existing 21:00 cutoff. No infinite loop or retry of a corrupt checkpoint.
2. Resolve local date and 08:30 UTC cutoff; discover latest successful trusted `daily_market_brief.yml` artifact completed **before** that cutoff. Never substitute a run that completed later; a delayed report run may still use only valid pre-cutoff data.
3. Run the existing pipeline for normal intraday output. Morning checkpoint discovery occurs first within its own step; if a valid dated report exists, reuse it byte-for-byte, even if current data changed.
4. When no checkpoint exists, verify the selected pre-cutoff `daily_intelligence.json`, `top_intelligence.json` and manifest hashes, report dates, validation, item evidence references and source timestamps. Reassess each Top item's existing freshness threshold at 08:30. A stale **artifact aggregate** cannot invalidate unrelated current validated items. The old aggregate/source warning remains visible.
5. Morning minimum useful gate: at least 2 current validated non-data-quality Top items; at least 2 distinct related assets; at least one eligible cross-asset signal or regime story supported by signal references; daily and Top artifacts not unavailable; manifest provenance integrity; no source/item future leakage. Missing calendar or one reference asset is nonblocking. If this gate fails, no canonical checkpoint is created.
6. Create only the public-safe projection on the protected dated branch. Collision loads and validates the winner; corruption, wrong provenance or absent branch fail closed. Pages publishes a dated report only when validated.
7. Every successful build publishes `morning_delivery_status.json`. When no valid report exists, `morning_report_public.json` stays absent. The status JSON states `pending_source` or `unavailable`; it never serves a prior-day report as today's. A checkpoint verification failure writes `failed` locally, fails the build and retains the prior Pages deployment, so it cannot remove an already published valid report. Actions logs retain the failure state. Other daily intelligence remains available from the prior deployment.

## 2026-09-24 root cause

Scheduled run [35958991007](https://github.com/froyo1015/AI-Market-Intelligence/actions/runs/35958991007) began at `2026-09-24T05:13:26Z` (13:13 Taipei), hours after the target. It downloaded the pre-cutoff successful run `35832903568` from September 23. That run's daily and Top **aggregate** `source_timestamp` was `2026-09-21T04:00:00Z`; at 9/24 08:30 its 48-hour artifact threshold had elapsed. Both selected Top items, however, had their own current evidence windows: the USD/FX observation from 9/22 23:00 UTC and BTC/ETH from 9/23 00:00 UTC, still inside their 48-hour item threshold at the 9/24 cutoff. The old Morning builder required both aggregate artifacts to be current, so it marked the whole candidate unavailable. The checkpoint then returned `source_unavailable_no_checkpoint`. No dated 9/24 file exists on `morning-reports`; the CLI produced no public Morning JSON, and its allowed failure did not stop Pages. The published 404 is a **source gate / checkpoint creation failure**, not a Pages transport failure. This diagnosis was verified by downloading the exact prior run artifact and replaying the fixed cutoff offline. Its result after the candidate fix is partial with 2 valid Top items and an explicit stale aggregate warning. This is not a retrospective production Morning Report and was not published.

## Failure meaning and bounds

`pending_source` means the scheduled retry may still create the first valid date file. `unavailable` means the final scheduled retry or later same-day manual attempt has no valid source; an administrator may still perform explicit recovery if legitimate pre-cutoff evidence exists. `failed` means checkpoint trust/transport/validation failed; do not overwrite it. `created` and `reused` require a matching validated public report with hash. Retry count is the scheduled attempt ordinal (0–1), not a count of all Actions invocations. A workflow can publish other outputs while Morning status is unavailable; the public status and workflow warning distinguish that from a delivered report.

## Remaining guarantee limit

GitHub scheduled workflows do not provide hard punctuality. Two bounded scheduled attempts improve opportunity but cannot force an 08:30 start or create current evidence where none exists. Daily delivery is production-ready only after a live 08:30-window create, a same-day reuse, a later-source-change reuse, and next-day rollover observation or deterministic rollover test. Public artifact hashes and dates must match the canonical checkpoint.
